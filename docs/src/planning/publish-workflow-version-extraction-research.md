# Publish Workflow Version Extraction Research Dossier

## Goal And Trigger

`publish-crate-detritus-protocol.yaml` (generated by simit) failed in CI with:

```
Tag 0.1.0 does not match Cargo.toml package version 0.1.0
0.1.0
0.1.0
⚙️ [runner]: exitcode '1': failure
```

The tag and the "package version" print as the same string yet the equality test rejects them. The user wants the root cause located inside the simit publish-workflow generator and a fix that prevents this for any downstream consumer.

## Current Reality

Reproduced locally against the detritus workspace
(`/data/nvme0/can/Projects/detritus`, three workspace members all at `0.1.0`):

```
cargo metadata --no-deps --format-version 1 \
  | grep -m1 -o '"version":"[^"]*"' \
  | cut -d '"' -f4
# →
# 0.1.0
# 0.1.0
# 0.1.0
```

`$version` is captured as the multi-line string `0.1.0\n0.1.0\n0.1.0`, while
`$tag` is `0.1.0`. `[ "$tag" != "$version" ]` is therefore true, and the
`echo "Tag $tag does not match Cargo.toml package version $version"` renders
exactly the observed log (one inline `0.1.0`, two trailing-line `0.1.0`s).

The defect is in the simit generator, not in the consumer repo:

- [simit/src/render/ci.rs:1648-1665](../../../../simit/src/render/ci.rs#L1648-L1665)
  emits the validation snippet for every publish-crate workflow.
- The snippet relies on `grep -m1 -o` to "pick the first version".
- GNU `grep -m NUM` limits _matching lines_, not _match occurrences_. `cargo
metadata` outputs a single-line compact JSON document, so every workspace
  package's `"version":"…"` substring is on the same matching line and `-o`
  prints all of them. `-m1` does not truncate them because grep never reaches a
  second matching line.
- On a single-crate repo this is silently fine (only one package, one match).
  On a Cargo workspace it is always wrong: even when every member happens to
  share a version the resulting `$version` is multi-line and the equality test
  fails.

Independent of that bug, the snippet has a second latent defect: it never
filters cargo metadata to the package the workflow is publishing. Once any two
workspace members diverge in version, the workflow would compare the tag to
whichever package appears first in `packages[]` — typically the
alphabetically-first member, not the package being published.

## Work That Should Survive Into The Long-Term Plan

1. **Fix the version extractor in `validate_release_tag_step`.** Replace the
   `grep -m1 -o … | cut` pipeline with one of:
   - `cargo metadata --no-deps --format-version 1 --manifest-path crates/<pkg>/Cargo.toml`
     and parse, or
   - `cargo metadata --no-deps --format-version 1` piped through `jq -r
--arg name '<package-name>' '.packages[] | select(.name==$name) | .version'`
     (preferred — jq is already required elsewhere in simit-generated CI,
     verify before committing), or
   - Use `cargo pkgid -p <package-name>` and strip the version suffix — no jq
     dependency, robust to workspace layout.
     The chosen approach must be parameterized by the _publishing package name_
     so the comparison is always against that package's manifest.
2. **Make package-scoping mandatory.** Pass the package name into
   `validate_release_tag_step` (today it only takes
   `cargo_metadata_command: Option<&str>`). Add a `package_name: &str`
   parameter and thread it through the publish_workflow callers in
   `src/render/ci.rs` so every emitted snippet filters by the right package.
3. **Test the workspace case.** Extend `tests/init_ci.rs` with a fixture that
   has ≥2 workspace members (different versions) and assert the generated
   publish workflow extracts the _publishing_ package's version, not the first
   one in `packages[]`. Also assert the script does not contain `grep -m1 -o`
   on cargo-metadata output. A snapshot-style assertion on the validate step
   would catch regressions of either bug at once.
4. **Regenerate downstream consumers.** Detritus is the known downstream;
   per-user simit registry should be checked for any other workspace consumers
   that need their publish workflows regenerated after the fix lands.
5. **Patch release.** Bump simit to a patch release (e.g. 0.15.1) once the fix
   and tests are in, so dependents can take it via `simit init-ci` regen.

## Blockers And Missing Artifacts

None. Reproduction is deterministic locally, the generator source is
checked in, and the failing CI log matches the local reproduction byte-for-byte.

## Risks And Constraints

- **Tag→version comparison drift on workspaces.** Until the generator is
  fixed, every workspace publishing through simit is exposed to this false
  positive. Workspaces where members share a version see it as a hard CI
  failure (current detritus state). Workspaces with diverging versions would
  see _silent incorrect comparisons_ if all members happened to be the
  alphabetically-first one being tagged — riskier.
- **jq availability.** If the fix uses `jq`, the generated step must ensure
  `jq` is present in `rust:1.88-bookworm` (it is not preinstalled). Either add
  an apt-get install step alongside the existing gpg/curl bootstrap, or pick
  `cargo pkgid` / `--manifest-path` approaches that need no extra tools.
- **Generated-file drift.** `# Generated by simit. Manual edits will be
reported as ci=drift.` — downstream consumers can't hand-patch the workflow
  without triggering simit's drift detector. The fix must ship in simit and
  flow out via `simit init-ci`.
- **Other places that may use the same pattern.** Only one occurrence found in
  `src/`; verify also against `src/init_ci.rs`, `src/render/`, and any release
  chaperone hook templates before declaring the audit complete.

## Candidate Phase Boundaries

1. **Phase 1 — Generator fix + tests in simit.** Refactor
   `validate_release_tag_step` to accept the package name and emit a
   workspace-correct extractor; add a multi-member workspace fixture under
   `tests/init_ci.rs`; verify with `cargo test -p simit`. (Small phase, single
   crate.)
2. **Phase 2 — Release simit patch and regenerate dependents.** Bump version,
   update CHANGELOG, publish via the existing simit release flow; then invoke
   `simit-dependent-fixes` to regenerate `publish-crate-*.yaml` on detritus
   (and any other workspace consumer in the registry), commit and push.
3. **Phase 3 — Re-attempt the detritus 0.1.0 publish.** Once detritus has the
   regenerated workflows, re-trigger the tagged release for
   detritus-{client,protocol,server} and confirm the validate step passes.

These can run sequentially; Phase 2 is gated on Phase 1 being merged and
released, and Phase 3 is gated on Phase 2.

## Open Decisions For The User

- **Extractor approach** — `cargo pkgid` (no new deps), `jq` (cleaner but
  needs apt install in the container), or `--manifest-path` + grep (close to
  current shape, easiest diff). Recommendation: `cargo pkgid -p <name>` then
  `awk -F'#' '{print $2}'` (or split on `@` on newer cargo). Avoids new
  runtime dependencies, robust on any workspace layout.
