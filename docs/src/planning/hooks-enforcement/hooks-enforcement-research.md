# Hook Enforcement Research Dossier

## Goal And Trigger

User reported a clippy `cognitive_complexity` failure in detritus CI that was
not caught by any local pre-commit / pre-push hook. Expectation: pre-commit
hooks generated by `git-hooks.nix` should run `cargo clippy --all-targets
--all-features -- --deny warnings` before push, matching the CI command at
[detritus .forgejo/workflows/ci-detritus-server.yaml:34](/data/nvme0/can/Projects/detritus/.forgejo/workflows/ci-detritus-server.yaml).

Investigation surfaced a fleet-wide problem: across every project the simit
registry currently labels `hooks: installed`, no per-project hooks actually
fire on commit or push. The label is wrong and the underlying enforcement
chain is broken at three distinct layers.

This dossier captures the evidence so a multi-phase plan can decide how
simit, canix, and downstream projects should be repaired.

## Current Reality

### What the user has

- A NixOS host with a home-manager git module that sets a system-wide
  `core.hooksPath` pointing at a Nix store directory containing only a
  `commit-msg` hook (strips AI co-author trailers).
  Source: [canix home/modules/development/vcs/git.nix:34](/data/nvme0/can/Projects/canix/home/modules/development/vcs/git.nix#L34).
- The module also sets `init.templateDir` to seed `.git/hooks/commit-msg`
  on `git init` / `git clone`, but seeds nothing else.
  Source: [canix home/modules/development/vcs/git.nix:14-18](/data/nvme0/can/Projects/canix/home/modules/development/vcs/git.nix#L14-L18).
- Multiple Rust projects with `nix/pre-commit.nix` declaring fmt, clippy,
  audit, treefmt, MSRV, and `nix flake check` hooks via `git-hooks.nix`.

### What actually runs

- `git push` runs no pre-push hook in any registered project.
- `git commit` runs only the global `commit-msg` (AI signature strip);
  no fmt/clippy/audit.
- `pre-commit install` (invoked by the git-hooks.nix `shellHook` inside
  `nix develop`) aborts with:
  > `[ERROR] Cowardly refusing to install hooks with core.hooksPath set.`
  > This is a documented pre-commit behavior: it refuses to write
  > `.git/hooks/*` when git is configured to look elsewhere, to avoid
  > silently installing hooks that git will not execute.
- Net effect: every project that "has" pre-commit configured has zero
  pre-commit enforcement locally. CI is the only gate.

`simit projects list --json` (simit 0.14.1) currently labels these projects
`hooks: installed` while none of them actually have working hooks:

| Project             | simit says | `.git/hooks/pre-commit` | `.git/hooks/pre-push` | `nix/pre-commit.nix` |

`skillctl` shows the detector is doubly broken: the registry still reports

Code: [simit src/registry.rs:582-588](/data/nvme0/can/Projects/simit/src/registry.rs#L582-L588) —
`detect_hooks_status` only checks for the presence of `nix/pre-commit.nix`.
It never inspects `.git/hooks/`, never consults `core.hooksPath`, and

## Work That Should Survive Into The Long-Term Plan

### Required outcomes

1. **Simit hook detection must reflect reality.** A `installed` label must
   only appear when a pre-commit / pre-push hook would actually fire on
   `git commit` / `git push`.
2. **Simit must expose a `hooks install` (or equivalent) command** that can
   wire hooks into the resolved hook directory, regardless of whether
   `core.hooksPath` is set system-wide. Today the only install path is
   the `git-hooks.nix` shellHook, and it silently aborts.
3. **The canix global-hooks system must not block per-project hook
   enforcement.** Either it dispatches to both system _and_ per-project
   hooks, or the global hook moves out of `core.hooksPath` entirely.
4. **Detritus and every other affected project should commit a healthy
   hook setup** (or `simit projects show ... hooks: installed` should be
   replaced with a more granular state that makes the breakage visible
   to the user during routine status checks).

### Constraints to preserve

- The AI co-author strip in `commit-msg` is a user requirement and must
  keep running on every commit.
- pre-commit's "cowardly refusing" guard is correct and should not be
  bypassed by sidestepping `core.hooksPath` blindly — pre-commit refuses
  because writing into `.git/hooks/` while `core.hooksPath` points
  elsewhere produces hooks that git silently ignores.
- The `nix develop` shellHook entry point is convenient but is not the
  right place to _enforce_ installation, because (a) users may operate
  outside devShells, and (b) silent failures are how we got here.

## Risks And Constraints

| Risk                                                                                                                                                                                                               | Mitigation needed                                                                                                                                                                                                    |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A naive "chain hook" wrapper that calls both system and project hooks may not match pre-commit's expected install layout (pre-commit writes a specific wrapper script that re-execs itself with `pre-commit run`). | The dispatcher must call into pre-commit by `pre-commit run --hook-stage pre-commit` rather than execing `.git/hooks/pre-commit` directly, to avoid double-wrapping or breaking pre-commit's environment activation. |
| Changing `core.hooksPath` system-wide could unintentionally disable existing per-project setups in non-canix Rust projects on the same machine.                                                                    | Phase the change carefully; provide a `canix repo hooks` migration in the canix CLI (a `hooks.rs` already exists at `/data/nvme0/can/Projects/canix/cli/src/commands/repo/hooks.rs` — likely the right home).        |
| Simit detection that reads `.git/config` and `core.hooksPath` adds a non-trivial git-dependency surface.                                                                                                           | Use `git2` (already in simit's tree if present) or shell out to `git config --get core.hooksPath`; both are well-bounded.                                                                                            |
| Existing `init.templateDir` only fires on `git init`/`git clone`. Already-cloned repos must be back-filled by a one-shot migration.                                                                                | The simit `hooks install` command (or `canix repo hooks sync`) is the right vehicle for this; do not rely on re-cloning.                                                                                             |
| The `skillctl` stale-entry case shows `simit projects scan` is not re-detecting all features. Whether this is scope-limited or a broader bug needs confirmation.                                                   | Add a phase to audit `projects scan` re-detection coverage; out-of-scope for the core hooks fix but worth surfacing.                                                                                                 |

## Candidate Phase Boundaries

These are likely phase slices for a downstream multi-phase plan. Routing
language deliberately omitted — that belongs to the chosen planner.

1. **Simit: replace presence-based hook detection with reality-based
   detection.** New states: `configured` (config file present),
   `installed` (hooks actually wired and would fire — verified by
   resolving `core.hooksPath` and checking the resolved directory),
   `conflicted` (config present but hooks blocked by a foreign
   `core.hooksPath`). Update registry schema, detection code, formatter,
   and tests. Include a migration for stored registry data.
2. **Simit: add `simit hooks install` (and `--check`) subcommand.**
   Resolves the target hook directory, runs `pre-commit install
--install-hooks --hook-type pre-commit --hook-type pre-push` (and
   commit-msg if configured), and emits a clear actionable error if
   `core.hooksPath` blocks installation. Mirror the existing
   `simit init flake/ci --check --diff` shape.
3. **Canix: stop blocking project-level hooks at the system level.**
   Either drop the global `core.hooksPath` and rely on `init.templateDir`
   to seed `commit-msg` per repo (with a `canix repo hooks sync` sweep to
   back-fill existing clones), or switch the global hooks path to a
   dispatcher that defers to `.git/hooks/<name>` after running the system
   step. The first option is simpler and removes the conflict at its
   source.
4. **Fleet sweep: install hooks across all registered Rust projects.**
   Once phases 1-3 are in, run `simit hooks install` on every project
   currently showing `configured` (post-rename from `installed`).
   Validate by checking the new detector flips them to `installed` and
   by invoking `cargo clippy` via the hook on a fresh sanity-check
   commit in detritus.
5. **(Optional, observability)** Add a `simit doctor` or extend
   `simit projects list` so `conflicted` projects surface visibly in
   day-to-day workflows — preventing this class of silent failure from
   recurring.

Phases 1 and 2 are simit-only and can run in parallel with phase 3
(canix), but phase 4 must follow all three. Phase 5 is independent and
can run anytime after phase 1.

## Open Decisions For The User

1. **Resolution direction for canix:** drop the global `core.hooksPath`
   and rely on `init.templateDir` + per-project hooks (clean, but every
   already-cloned repo needs a one-shot `commit-msg` install), or build a
   dispatcher hook directory that re-execs `.git/hooks/<name>` after the
   global step (preserves the current "AI strip works automatically on
   new clones" property but is more code to maintain).
2. **Whether `simit hooks install` should be invoked transparently from
   `simit init flake` / `simit init ci`** or kept as an explicit
   subcommand. Bundling it makes new-project setup one step shorter but
   muddies the boundary between "files on disk" (init) and "git state"
   (hooks).
3. **Whether to keep the registry feature key as `hooks` with new states,
   or split into `hooks_config` + `hooks_installed`.** New states is less
   churn; split is more explicit and survives future hook frameworks
   beyond `git-hooks.nix`.
