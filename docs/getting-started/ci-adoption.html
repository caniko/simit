CI Adoption Notes

This page captures the operational rules learned while moving existing Codeberg-hosted Rust repositories from hand-rolled Forgejo Actions workflows to simit init ci.

Generator Contract

Generated workflow files are owned by simit and include:

# Generated by simit. Manual edits will be reported as ci=drift.

After the first non-check simit init ci run, simit persists the effective CI options into simit.toml under [ci]. The canonical drift check is then:

simit init ci --platform <forgejo|github> --check --diff

When a project has not yet persisted its CI options, the drift error still prints the full regeneration command with the effective runtime, runner, workspace, and optional gates so the migration path stays explicit.

Persisted CI settings look like:

[ci]
platform = "forgejo"
runtime = "nix"
runner = "atlas"
workspace = true
with_deny = true
with_audit = true
with_docs = true
with_msrv = true

Generic CI vs Release Publishing

Rust CI and crates.io publishing are separate modes. By default, simit init ci generates ordinary CI workflows even when a package has crates.io metadata. It does not generate publish-crate*.yaml or keys/maintainers.gpg unless release publishing is enabled explicitly or inferred from existing generated release workflows.

Enable crates.io release workflows with:

simit init ci --platform forgejo --publish-crates

Persist the choice when a project owns release publishing:

[ci]
publish_crates = true

Pass --publish-crates=false or set publish_crates = false to keep a project CI-only even when stale generated publish workflows are present. Release artifact and package-manager publishing flags such as --with-artifacts, --with-homebrew, --with-chocolatey, and --with-scoop imply release mode.

For a Forgejo Nix workspace with release artifacts and cargo-deny:

simit init ci --platform forgejo --runtime nix --runner atlas-nix-trusted \
  --workspace --with-artifacts --with-deny --check --diff

If the project also publishes a Homebrew tap, keep the tap metadata in project config when possible. Command-line overrides work, but config makes future checks shorter and reproducible.

Flake-Integrated Rust Projects

--runtime auto selects the Nix runtime when flake.nix exposes meaningful project outputs such as packages, apps, checks, devShells, NixOS or Home Manager modules, or top-level lib. Cargo-only projects and placeholder flakes stay on direct Cargo CI.

For existing custom flakes, keep project-owned outputs intact and let simit manage hook wiring with:

simit init flake --scope hooks-only
simit init ci --platform forgejo --runtime nix

Non-Publishable Crates

Cargo represents publish = false in metadata as an empty publish list. Simit treats that as a hard opt-out from crates.io publication:

  • CI still runs tests, optional policy gates, and clippy for the package.
  • CI skips cargo package for that package.
  • Simit does not generate publish-crate-<package>.yaml for that package.

This matters for workspace utility crates such as xtask. They often depend on unpublished git-only helper crates, so cargo package -p xtask fails even though the crate is intentionally not publishable.

When converting a workspace, delete any stale generated publish-crate-*.yaml for publish = false members after regenerating CI. Check mode reports those stale generated files as extra.

Cargo-Deny Policy

--with-deny means generated workflows install and run:

cargo deny check bans licenses sources

The policy file is project-owned:

  • If deny.toml is missing, simit bootstraps a conservative default.
  • If deny.toml already exists, simit leaves it alone.
  • Check mode does not treat local license or source allow-list changes as generated CI drift.

Validate policy changes with the same cargo-deny version used by generated CI:

CARGO_HOME=/tmp/simit-cargo-deny-0183
cargo install cargo-deny --locked --version 0.18.3
"$CARGO_HOME/bin/cargo-deny" check bans licenses sources

Do not assume a newer local cargo-deny accepts the same license identifiers as the pinned CI version. For example, cargo-deny 0.18.3 expects the older GPL allow-list spelling GPL-3.0 rather than GPL-3.0-only.

Forgejo Nix Runtime Details

Forgejo Nix-runtime workflows intentionally set:

env:
  NIX_CONFIG: "experimental-features = nix-command flakes"
  XDG_CACHE_HOME: "/tmp/.cache"
  CARGO_HOME: "/tmp/.cargo"

CARGO_HOME must be absolute. Relative cargo homes can make cargo install panic or write into surprising paths under Forgejo/act containers.

Generated Nix-runtime workflows also add $CARGO_HOME/bin to PATH before installing optional cargo tools. Optional tools should be installed into the workflow cargo home, not assumed from the runner image.

MSRV checks under Nix use the dev shell’s cargo:

nix develop -c cargo check --all-targets

They do not use cargo +<msrv> because Nix dev shells do not imply rustup toolchains.

Cargo-Audit Reliability

Generated cargo-audit steps fetch the RustSec advisory database explicitly and then run audit with a local database:

git clone --depth 1 https://github.com/RustSec/advisory-db.git "$db"
cargo audit --db "$db" --no-fetch --stale

This avoids repeated network fetch behavior inside cargo audit itself and makes failures easier to separate into “could not fetch advisory DB” versus “advisory gate failed”.

Runner Debugging

When Codeberg/Forgejo runners are flaky, separate stale runs from fresh runs:

  1. Push or rerun on a new commit so the head SHA changes.
  2. Poll only runs created for that head.
  3. Inspect exact run logs before changing code.

Use the repository metadata command first when using the Codeberg workflow:

berg --owner-repo caniko/<repo> repo info

Then poll runs through the Codeberg API if the local berg build does not have Actions subcommands:

curl -fsSL "https://codeberg.org/api/v1/repos/caniko/<repo>/actions/runs?limit=10" |
  jq -r '.workflow_runs[] | [.id, (.html_url|split("/")[-1]), .status, .workflow_id] | @tsv'

A failure like Input/output error (os error 5) while rustc writes metadata is runner/storage instability. A failure from cargo package, cargo deny, or a crate test is a project or generator issue until reproduced otherwise.

Fleet Adoption Checklist

For each repository:

  1. Rebase the adoption branch onto the default branch.
  2. Regenerate CI with the project’s intended options.
  3. Run simit init ci ... --check --diff.
  4. Run the relevant local package checks that failed in CI.
  5. Push one repo-scoped branch.
  6. Watch fresh Codeberg runs for that branch head only.
  7. After merge, verify at least one green default-branch CI run.

Fleet-level verification:

simit projects scan
simit projects list

The converted repositories should no longer show ci(hand-rolled). Projects with only generated workflows show ci(managed). Projects with generated CI plus supplementary non-generated workflows show ci(managed+extra).
